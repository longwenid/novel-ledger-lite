# 章纲预检与跨章复审

用于长篇连续执笔的准备与复审，不负责替作者设计故事。已有账本管可枚举的状态，实际阅读判断
故事是否仍兑现确认的内容。两者都通过，也不能保证所有语义错误或文学问题已经消除。

## 先核验章纲，再写正文

开写前先实际只读作者确认的总纲、卷纲和连续剧情单元的章纲，再对照初始状态核验；
不先补写正文替设计找理由。沿连续章节分别判断因果可行与阅读驱动，不能把章名有吸引力、
字段齐全或没有硬伤当作两者都成立。

| 核验对象 | 应能从既有设计中回答的问题 |
| --- | --- |
| 方向与章节职责 | 本卷怎样推进 `reader_promise/story_engine/ending`？各单元实际改变什么？是否连续只安排准备，却没有已计划的结果？ |
| 人物动机 | 当前欲望、所知与限制为何使他作此选择？若目标或关系改变，哪次经历、选择与后果支撑转变？ |
| 能力与破局 | 所需能力、资源和信息此前是否具备？新能力的来源、代价、适用范围及尚不能做到的事是否明确？不能把“灵机一动”当作缺失前提。 |
| 时间与归属 | 移动、修行、伤势、交易和消息能否按同一条时间线成立？所有权、保管权、承诺给付与实际交割是否分清？ |
| 承诺与兑现 | 承诺的有效期限、兑现内容和后果是否匹配？“再次提起”“另约时间”是否被误当作已兑现？允许有意延宕，须符合设计并承担相应后果。 |
| 单元的阅读驱动 | 读者眼下具体期待什么？人物的选择怎样改变局面或关系？已兑回报带来了什么后果，而非只在账上完成一次？ |
| 相邻单元 | 连续单元是否反复使用同一种准备、验证、解释与收束？即使各自因果成立，实际变化和具体期待是否仍在推进？ |

输入以现有字段承载：长期约束进契约；有效人物状态、知情与资源进对应账；节点、线路和具体伏笔
进已有叙事记录；本章职责与预期阅读效果用章纲支持的字段表达。格式见 [inputs.md](inputs.md)。
不要另建一份会独立更新的“人物现状总表”作为第二真源，也不要为通过校验编造未知金额、时间或结局。
人物推测、未来计划和作者真相分别标明；未知数不填零，口头约定不写成已获得。
派工前对照真实 current 核查场景动机与当次利益：初始人物档案和通用模板不得把已完成的阶段目标
重置为当前任务，也不得套用不适合本场景的诉求或压力。以语义和经历判断，不能凭字符串是否相等
自动判冲突；发现矛盾，由准备者先修允许调整的未写材料再发包，写作者不临时改设定圆场。

记录实际核验的来源版本、覆盖范围、冲突及待核实项。重要前提缺失、相邻因果不成立或与确认方向
冲突时，退回准备者处理；不得宣称“整卷预检通过”。源文件转换成功、状态链模拟成功和语义预检通过
是三件事，应分别报告。已确认设计本身需要调整时，提出具体问题及影响，由有设计权限的流程修订；
本技能不因预检而取得改写总纲的授权。

章纲应锁定结果、必要原因和边界，并分清本章必须发生的动作、抉择与须遵守但不必复述的限制，
不用新增字段。能力、归属与仙法边界是后台执行条件，不要求每章都写成说明对白。首次建立、
影响当次选择或负载改变时，展开到读者足以判断；沿用条件可用动作体现。必要材料仍完整携带，
约束不因少解释而减弱。正文自由选择成立的动作、对话和感官细节，不必预编每次停顿；
过细的操作说明也不能替代人物抉择。

## 每章审读如何覆盖叙事

`core_context` 已携带方向与主角约束，写作者和独立读者都须实际使用。沿用现有六类报告：

- `outline.notes`：说明本章是否履行既定职责，是否符合核心承诺与生效文风；不能只有“符合章纲”。
- `causality.notes`：说明关键选择、能力进展和人物变化如何由已知动机、前提与后果支撑。
- `continuity/unplanned`：同时核对仍有效的限制、未兑承诺及正文暗中新增的例外；其余检查照旧。

违反已确认内容用 `reject`；需要的证据或设定缺失用 `needs_material`。阅读偏好与设计缺陷应区别：
慢节奏、慢热、静章、主角暂不出场或没有升级，本身不构成漂移；不强求任何题材都有金手指、战斗或商业钩子。
人物允许因经历而改变，也不要求把隐含动机全部写成解释对白。

## 组末与卷末实读

单章都成立，也可能累积为主线空转、动机偷换、承诺反复延期或声线同质化。每组末及卷末由不同于
写作者的独立读者，通读对应的连续正文，结合冻结核心、本卷职责、有关旧章和当前状态判断。
长卷可分连续单元阅读，但须保留覆盖记录，再复核单元之间的因果与全卷承诺；摘要和锚句不能冒充全文。

可复用末章的入账前审读，不必新增一种账本或审读格式。末章尚未写时，准备者将组内已提交章全文
及必要的旧章加入同一包，再沿原流程派工与审读：

```python
package = pipeline.chapter_package(
    book, store, chapter, group_row,
    extra_chapters=group_previous_chapters + relevant_older_chapters,
)
# 写作者按校验后的包完成 draft；再将原流程产生的完整请求交独立读者。
review = pipeline.review_request(book, store, chapter, draft, writer=writer_id)
# 实际报告仍由 record_content_review 登记，不能把本示意代码当成通过报告。
```

准备者负责安排覆盖范围；引擎不会自动推断本组所有语义前提，也不会自动执行组末阅读。
末章已提交后才开展的额外复审，记录为阶段审读，不能补发或替换旧章入账凭证。

报告沿用现有字段，在 notes 或阶段报告正文中分别列出下述两项结论；不新增协议字段：

1. 实际读了哪些完整章节、哪些仅为参考，并记录稿件版本或指纹。
2. **事实与动机连续性结论**：这段实际推动了什么，关键选择是否有动机，能力边界与承诺的推进、兑现或延宕是否成立。
3. **追读判断、具体期待与剩余叙事风险**：实际愿不愿继续读、具体想看什么；局面或关系怎样变化，已兑回报怎样产生后果，相邻单元是否同式。
4. 支持两项判断的跨章原文证据、最强反证、缺少的材料。只读了部分就缩小结论，不补造未读内容；区分正文执行偏差、章纲设计问题和纯粹偏好，给出具体位置。

不以数字评分、固定爽点频率或统一的篇幅比例代替判断。实际不想继续读也应如实写出；
愿再试几章不是稳定追读，更不是市场留存数据。两项结论可以不同，不能用事实与动机通过代替
追读判断。若指出了具体阅读驱动缺口，先按原有权限修订未写单元、重验后再派相关后续章，
不能凭 `submit.ok` 无限推进；不以静章、慢热或个人节奏偏好自动判失败。

## 发现问题与恢复

当前待提交稿的问题先返修、重包并重新审读。未写设计的问题按原有修纲权限处理，重验状态链；
需要更改已提交历史或根契约时，单独提出版本变更方案，不覆写旧账，也不通过换文风接口修改故事契约。
已经通过的历史报告不因后来补充了检查要求而自动拥有新增结论。

保存阶段时保留实际审读材料、报告与处理结论；阶段报告只是证据，不独立更新人物或资源状态。
新会话从账本恢复并重新签发包，不能凭聊天摘要接续，也不能因近窗之外没有展开就视作旧事实失效。
有未解决的方向冲突时先停止相关后续派工、定位问题，不把它留给正文临时圆场。

本流程依赖宿主与读者实际执行。现有格式和指纹约束能绑定所登记的材料与报告，不能证明读者真的理解了
人物、文风或因果；没有运行的步骤不得声称已由引擎自动保证。
